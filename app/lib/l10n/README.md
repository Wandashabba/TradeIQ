# Localisation (field app)

The field-agent flow is translated with Flutter's standard
[`gen-l10n`](https://docs.flutter.dev/ui/accessibility-and-internationalization/internationalization):

| File | Role |
|---|---|
| `../../l10n.yaml` | gen-l10n configuration |
| `app_en.arb` | **Template.** Every message, with `@key` descriptions and placeholder types |
| `app_af.arb` | Afrikaans |
| `app_localizations*.dart` | Generated by `flutter gen-l10n` (also runs on `flutter pub get`) — never edit by hand |
| `l10n.dart` | `context.l10n`, supported locales, locale resolution, date helper |

Shipped locales: **English (`en`)** and **Afrikaans (`af`)**.

Scope is the whole product: the field-agent flow (sign-in, Today, store picker,
visit/audit sections, submit, outcome, Your work, and the agent widgets) **and
the manager console**. The console started English-only and was translated
screen by screen as each one moved onto Torchlight; the reporting group
(Reports, schedules, run history, audit templates, webhooks, Messages) was the
last of it.

**A hardcoded English string on a screen that has an Afrikaans translation is a
defect**, and the worst version of it is a half-translated route: a manager taps
"Verslae" and lands on "Reports". `test/l10n/afrikaans_reporting_test.dart`
holds that line for the reporting screens in two ways — it pumps each screen at
`af` and asserts the English words are *absent*, and it reads the sources for
reader-facing English a rendering test could never reach.

Three kinds of string stay English on purpose, and each says so in its ARB
description:

* **wire values** — `visits`, `daily`, `report.generated`, the webhook event
  names. A value outside the allow-list falls back to its slug rather than to an
  invented translation.
* **formats and standards** — the ISO date shape the report filters store
  verbatim, `http://`, `HTTP`, `HMAC`, `POST`, `UTC`, `CSV`.
* **example values** — a hint like `https://example.com/hooks/tradeiq` is a
  shape, not prose.

## Using a message

```dart
import '../../l10n/l10n.dart';

Text(context.l10n.todayTitle);
```

`context.l10n` falls back to English when no localisation delegate is installed,
so a widget test that pumps a bare `MaterialApp` still sees English.

Dates: use `intl`'s `DateFormat` with `context.l10n.localeName` (see
`formatDayHeading`), never hand-built month/day names.

## Writing messages

- One sentence is one message. Never glue translated fragments together.
- Numbers and names are placeholders, declared with a type in `app_en.arb`.
- Counts use ICU plurals: `{count, plural, =1{1 photo} other{{count} photos}}`.
- Keep product terms (TradeIQ), SKU codes and units untranslated.

## Choosing the language

The app follows the device language: a supported device language wins
(`af_ZA` → Afrikaans), anything else falls back to English. An agent can
override it from the translate icon in the agent app bar (System / English /
Afrikaans); the choice is persisted by `core/l10n/app_language_controller.dart`
the same way the theme mode is.

## Adding a locale

1. Add `app_<code>.arb` with `"@@locale": "<code>"` and a translation for
   **every** key in `app_en.arb` (no `@` metadata needed).
2. Add `Locale('<code>')` to `appSupportedLocales` in `l10n.dart`, and a value to
   `AppLanguage` in `core/l10n/app_language_controller.dart` plus a menu label
   message (the language's own name, e.g. "isiZulu").
3. Check that `flutter_localizations` supports the locale for Material's own
   strings; if it does not, a fallback Material delegate is needed.
4. Run `flutter gen-l10n` and `flutter test` — `test/l10n/arb_completeness_test.dart`
   fails if any key or placeholder is missing.

**Further South African languages (isiZulu, isiXhosa, Sesotho, Setswana, …)
must come from professional translators** who know retail and field-sales
vocabulary, and should be reviewed by native-speaking field staff before
release. Do not add machine-translated ARB files: a wrong instruction in an
audit ("count the facings", "do not submit") produces wrong data.
